## 3. Пункт 2: восстановление S-блока и расчёт DDT

На скриншоте `img/datutor/sbox1.png` видна увеличенная таблица DDT S-блока №1.
Она была перенесена в отчёт вручную и проверена двумя независимыми способами:

- **контроль сумм:** каждая строка DDT в сумме даёт 16 (всего 16 входов) — сошлось для всех 16 строк;
- **сверка с экраном «Уязвимости S-блоков»** (`img/datutor/vuln.png`): приложение показывает
  0x3→0xC, 0xC→0xF, 0xF→0x3 с P = 0,75 и 0x1→0x1, 0x2→0xD, 0x4→0x4, 0x5→0x5 с P = 0,625.
  Все семь значений в точности совпали с транскрибированной таблицей.

Дальше по DDT был **восстановлен сам S-блок** (`tools/recover_sbox.py`, перебор с отсечением):

```
S = [0, 1, 13, 12, 4, 5, 9, 11, 7, 10, 6, 8, 15, 14, 2, 3]
```

Важная оговорка для защиты: DDT не определяет S-блок однозначно — у `S'(x) = S(x ⊕ a) ⊕ b`
точно такая же DDT. Поэтому найден представитель класса эквивалентности при `S(0) = 0`.
Для расчёта дифференциальных характеристик этого достаточно: DDT совпадает с точностью до бита.

Расчёт выполняется `tools/ddt.py`, вывод сохранён в `out/ddt_simple.txt`:
15 сильных характеристик, максимум 12/16 = 0,75.

## 4. Пункт 5: DDT S-блока «Магмы»

S-блок №1 «Магмы» задан ГОСТ Р 34.12-2015 (таблица π₀), он фиксирован и одинаков у всех:

```
S = [12, 4, 6, 2, 10, 5, 11, 9, 14, 8, 13, 7, 0, 3, 15, 1]
```

`python3 tools/ddt.py magma` → `out/ddt_magma.txt`. Результат:

- максимум DDT при ΔX ≠ 0 равен **4**, то есть P ≤ 4/16 = 0,25;
- порог уязвимости P > 0,25 не превышен ни разу → **сильных дифференциалов нет**;
- для сравнения у упрощённого шифра максимум 12 (P = 0,75) и 15 сильных характеристик.

Это главный содержательный вывод работы: именно поэтому упрощённый шифр ломается
дифференциальной атакой за 200 пар, а «Магма» — нет.

⚠ На скриншоте из старой презентации (`img/magma/ddt_out.png`) в списке сильных
характеристик фигурирует строка ΔX = 0, ΔY = 0, P = 1. Это тривиальный случай
(одинаковые входы дают одинаковые выходы), в анализе он не учитывается — в нашем
расчёте строка ΔX = 0 исключена явно.

## 5. Пункт 3: картинка ФИО в режимах ECB и CBC

Сделано программно, `tools/make_modes.py`:

1. средствами PIL нарисована картинка 600×400, 24 бита, с текстом «Щеглов М.А.»
   (синяя рамка + белое поле — как в исходнике) → `img/modes/src_fio.bmp`;
2. массив пикселей зашифрован DES в режиме ECB, 54-байтный заголовок BMP оставлен открытым
   (иначе файл перестаёт быть картинкой — так же поступает и CrypTool);
3. то же самое в режиме CBC с тем же ключом и вектором инициализации;
4. результаты сохранены и как `.bmp`, и как `.png` для вставки в отчёт.

Параметры: ключ `0123456789ABCDEF`, IV `0001020304050607`.
Размеры выбраны так, чтобы массив пикселей делился на 8 байт: 600 × 3 = 1800 байт на строку
(кратно 4), 1800 × 400 = 720 000 байт (кратно 8) — дополнение не требуется.

DES берётся из OpenSSL 3 через legacy-провайдер (`-provider legacy -provider default`),
потому что в OpenSSL 3 DES по умолчанию отключён. Корректность проверяется в самом скрипте
эталонным тест-вектором: ключ `133457799BBCDFF1`, блок `0123456789ABCDEF` → `85E813540F0AB405`. ✔

Результат вышел хрестоматийный:

| Файл | Размер PNG | Что видно |
|---|---|---|
| `src_fio.png` | 6 263 б | текст, однотонный фон, рамка |
| `enc_ecb.png` | 11 895 б | текст и рамка отчётливо читаются |
| `enc_cbc.png` | 721 402 б | равномерный шум |

Разница в сжимаемости в 60 раз — хорошее количественное подтверждение того, что ECB
сохраняет избыточность исходных данных. Этот довод стоит привести на защите.

## 6. Блок-схемы

Рисуются нативными фигурами PowerPoint (их можно править прямо в презентации),
обозначения по ГОСТ 19.701-90. Генератор `build/flow.js` перенесён из ЛР №1.
Нарисованы заново четыре схемы: зашифрование DES, расчёт DDT, режимы ECB и CBC,
зашифрование «Магмы».

Тонкость генератора: конструкция `['if', …]` рисует ветвление, которое **всегда
возвращается в основной поток**, то есть идущий следом блок выполняется в обоих случаях.
Для взаимоисключающего выбора она не годится. На этом был допущен и затем исправлен
баг в схеме «Магмы»: выбор раундового ключа (прямой порядок в раундах 1–24, обратный
в 25–32) сначала был нарисован через `if` и читался так, будто оба присваивания идут
подряд. Заменено на один блок с явной записью обоих случаев:

```
i ≤ 24 → Ki = K[(i−1) mod 8]     (прямой порядок)
i > 24 → Ki = K[(32−i) mod 8]    (обратный порядок)
```

Проверка формулы: i = 1 → K0, i = 24 → K7, i = 25 → K7, i = 32 → K0. ✔
Это подтверждается и скриншотами: `img/magma/m1.png` (раунды 1–2: K0 = FFEEDDCC,
K1 = BBAA9988) и `img/magma/m3.png` (раунды 31–32: те же ключи в обратном порядке).

Длинные схемы (DES, DDT, «Магма») разбиты на две колонки через соединитель «А» —
иначе они сжимаются по высоте и текст становится нечитаемым.
